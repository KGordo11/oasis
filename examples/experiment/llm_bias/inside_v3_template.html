Inside LLM Bias V3

Do AIs favour posts written by their own AI? Three AIs from different companies (qwen3:8b by Alibaba, llama3.1:8b by Meta, gemma3:12b by Google) each play the same 100 made-up Americans on a pretend Reddit. Each AI's users write posts. Then each AI's users read every AI's posts. In V3 the actions really work: users see each other's comments, open profiles and posts, and send private messages.

This page shows the whole machine: what changed from V1 and why, every code file, the exact screen each AI was shown, every data file, and the cleaned data world by world and tick by tick.

01 · How V3 works

Each AI writes posts, then every AI reads every AI's posts, in a world where actions really happen

An AI is a large language model (a text-predicting program like ChatGPT) running on the Spark. A user is one of the 100 made-up people; the AI is handed that person's description and asked to act as them. A screen is one user looking at one thing and deciding what to do: one question to the AI.

The 3 × 3 grid: 9 worlds

Every AI reads every AI's posts. A world is one reader AI playing all 100 users, reading the posts one AI wrote. Posts are never mixed, and nothing in one world is seen in another. The diagonal is the baseline: an AI reading posts its own AI wrote.

Time runs in ticks

Everyone scrolls at the same pace. At tick 0 each of the 100 users reads the first post of their own scroll, at tick 1 the second, and so on, until each user has read every post except their own (99 users read each post). A user sees what other users did in earlier ticks, and their own actions at once. So at tick 0 nobody has commented on anything yet, like V1. Each tick later, more comments are on the screen.

Each user's scroll starts at a different place in one fixed order of the posts, so every post is read early by some users and late by others.

What one user does in one tick

  1. Sees one post screen

    The post, its comments with IDs (like [c12], the 5 newest), and a notice if new private messages are waiting. Vote counts are never shown. It is never told which AI wrote the post.

  2. Answers with a list of actions

    Any of the 27 OASIS actions plus open_messages, as JSON: zero, one or many. The answer example shows two entries. If the answer breaks a rule (an unknown action, a comment with no text), the AI is asked again with a new seed, up to 3 tries; then it counts as unreadable.

  3. The actions happen in the world

    An upvote is recorded, a comment appears under the post for later readers, a follow is made. OASIS's rules decide if it works: a second upvote on the same post fails, a comment ID that does not exist fails. Failed actions are saved with the reason.

  4. Look-up actions open a follow-up screen

    search_user shows up to 3 profiles (where a private message can be sent), search_posts and trend show lists of posts, open_messages shows the inbox, open_post opens a post from a list. The AI answers again there; at most 4 follow-up screens per post, then back to scrolling.

  5. Refresh

    A refresh with no reaction to the post brings the post back after the next one (a post is shown at most 5 times). This happened {{returns}} times in part 1.

02 · V1 → V3

What changed from V1, why, and what it did

V1 (rounds 101-102) was the first full Spark study. V3 changed four things. Three were first tested alone as "V1 + one change" (log 14.43-14.48, 20-23 Oct); the live world was tried in a 20-user pilot. The big sim then ran with all four on together. Part 1 is round 101 again: the same 100 users, and the posting turn uses the same random seeds as V1 round 101.

Kept exactly as in V1

  • The same 100 users with the same descriptions (file fingerprint ed110626), the same 3 AIs, the same engine settings for every AI (temperature 0.7, top_k 40, top_p 0.9, 8,192 tokens).
  • V1's prompts: the AI is not told which model it is (V2's "I am ..." line is off) and never told who wrote a post.
  • JSON-only answers on (tested off on 21 Oct: no real change; Gordon, 22 Oct: "it makes all AIs equal in response").
  • qwen thinking off, as in V1. Tested on (21 Oct): it changed qwen a lot (downvotes 14-21% → 31-36% of posts), only qwen can think so the AIs would be unequal, it is slow, and the bias answer was the same either way.
  • Part 1 shows V1's menu in V1's order (the same 27 lines). The order is the part 2 study.
  • One post per screen, vote counts hidden, users never see their own posts, the noise floor.

Tried and dropped (20-21 Oct)

  • A posting-only menu on the posting screen: 71% of qwen's users (thinking off) sent an empty list.
  • "Write as many posts as you'd like": very uneven post sets (149 / 244 / 266 posts).
  • Posting lines 2a and 2b: the "brand new Reddit" story leaked into 5-13% of gemma's posts.
  • A fixed flipped menu (least-used first): the biggest effect of all tests, so it became its own study. Part 2 ranks the menu from part 1's own data instead.

How the data is cleaned (every run, before any analysis)

  
    
    
  • Kept apart, never mixed into the main tables: noise-floor rereads (the _d1 files), unreadable answers,
    follow-up screens (profiles, searches, opened posts, inbox).
    • 
    
  • Merged: a post the refresh loop brought back counts as one post read.
    • 
    
  • Marked: every action is "done" (it worked) or "failed", with why.
    • 
    
  • Normalized: per 100 posts read, because the worlds have different numbers of posts.
    • 
    
  • Aggregated small to big: each world tick by tick, then each world all together, then totals.
    • 
    
  • Checked: posts read per world = posts × 99 and engagement = the published numbers, or nothing is written.
    No screen is lost: raw screens = posts read + refresh returns + unreadable + follow-up screens.

08 · Easy vs hard actions

  
Do the AIs pick the easy actions?

  
Some actions take one click. Others make the AI copy an ID from the screen, write text, or go to another screen first and
  then write (a private message: find the person, then type). Each action gets a level from what the menu and the live world
  ask for. 

  

    
LevelWhat it takesActions

    
1one clickupvote, downvote and take-backs, repost, follow, unfollow, mute, unmute, refresh, trend, open_messages, listen_from_group, back

    
2pick something on the screen (copy its ID)like / dislike / unlike / undo-dislike a comment, open_post, join_group, leave_group

    
3write textcomment, quote, report (needs a reason), search_user, search_posts, create_group

    
4write a whole postcreate_post (subreddit, title, body)

    
5go to another screen first, then writesend_message (from a profile or the inbox), send_to_group (open group chats, join, then write)

10 · Part 2: the menu order

  
Same posts, same users, the menu in a new order

  
Part 2 changes one thing. The 27 menu lines are the same words, but rank_menu.py puts them in a new order
  from part 1's own choices (all 3 AIs counted together, post screens only): in each group the action used least in part 1 goes on top, and the groups used least go first.
  Everything else is the same: the same 320 posts (checked byte for byte), the same 100 users, the same screens, the same
  seeds.

11 · On the Spark

  
The machine, the engine, and how long each step took

  

    

      
Machine: NVIDIA DGX Spark "honda" at the UK CS department: a GB10 chip with 121 GB of memory shared by the CPU and
      GPU. Another user (hsa303) runs GPU training jobs on it, which made these runs about 3-4× slower than on a free Spark.

      
Engine: llama.cpp (build b1-5e03bdd), one server per AI, only one loaded at a time, 8 answers at once, 8,192
      tokens per answer slot.

      
Models: qwen3:8b and llama3.1:8b (the Ollama files), gemma3:12b (ggml-org's gemma-3-12b-it Q4_K_M file).
