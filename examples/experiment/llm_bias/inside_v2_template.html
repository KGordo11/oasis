Inside the simulation

Do AIs favour posts written by their own AI? Three AIs from different companies each play the same 100 made-up Americans on a pretend Reddit. Each AI writes posts, then every AI reads every AI's posts. This page shows the whole machine: every code file (click to read it), what each AI is shown word for word, what it answered, how the Spark runs it, and every command used.

Two versions, one difference. V1 (rounds 101-102): the AI is given only the person to play. V2 (rounds 103-104): exactly the same, plus one line telling the AI which model it is, such as "I am Qwen3 8B, an AI model made by Alibaba, simulating this profile:". It is still never told who wrote a post. Comparing V2 with V1 asks: does knowing who it is change how much an AI favours its own AI's posts?

01 · The design

One round = a posting turn, a reading turn, then a wipe

An AI here is a large language model (a text-predicting program like ChatGPT) running on the Spark. A user is one of 100 made-up people. The AI is handed that person's description and asked to act as them. A screen is one user looking at one thing and deciding what to do: one AI call.

The 3 × 3 grid

Every AI reads every AI's posts, so each round fills nine cells. The diagonal is the baseline: an AI reading posts its own AI wrote. The other six are cross cells. Only one thing changes inside a column: which AI plays the reader.

The bias number

Some AIs simply upvote more than others, so comparing raw rates would be unfair. The double difference removes that:

bias(i, j) = (i reads i − j reads i) − (i reads j − j reads j)

It is computed on total engagement (every action across all 27, the main measure) and, as detail, on engaged % and upvotes. The first bracket asks how much more AI i engages with i's posts than AI j does. The second subtracts how much more i likes everything (measured on j's posts). Positive means i favours its own AI's writing. The 95% range comes from re-drawing posts and users 1,000 times (a bootstrap). If the range crosses zero, the data can't tell the bias from chance.

V1 and V2: the only change

Everything is identical in both versions: the same 100 users with the same full descriptions, the same 3 AIs and settings, both turns, every AI reading every AI's posts, baselines first, the noise floor. In V2 one line is added to the system message, right before the person's description, in both turns (decision LD-44). Each AI gets its own public name and maker, the way it names itself, not the engine's file name:

    V1 rounds and V2 rounds are never pooled together: each version has its own results and its own workbook.

    The change in run_v2.py (commits 09b28df, 50649e3; 9 Oct 2026):

    
      
    Rounds 101-102 still get the V1 prompt byte for byte (checked against the old text), so V1 can be re-run exactly.
      The preflight gained 2 checks for this (110 in all). Running the baselines first, or mixing AIs' posts, can't change an answer: every screen is a
      separate call with no memory and a seed fixed by round, poster AI, user and post.

    03 · Step by step
    
  
    What happens in one round, in order
    
  
      
    
    1. The runner loads one AI
      
      
      v2_night.py works through the round in a fixed order. Before each step it asks llamacpp_servers.sh only <AI>
      to make sure exactly that AI's server is running and the others are stopped, so only one model sits in the Spark's memory (≈13-15 GB).
      
      
      2. 
    
    2. Posting turn: 100 screens, one per user
      
      
      run_v2.py post builds one screen per user: the user's description, an empty feed, the five subreddits and the 27-action
      menu. Nobody is told to post. Whatever create_post actions come back become that AI's post set for the round.
      
      
      3. 
    
    3. Every call goes through one function
      
      
      llm.chat_json() sends the system message and the screen to the AI's server with the same settings for every AI
      (temperature 0.7, top-k 40, top-p 0.9, min-p 0, repeat penalty 1.0, thinking off) and asks for a JSON answer. Each screen has its
      own seed (a number that fixes the randomness), computed from the round, turn, AI, user and post, so a rerun gives the same draw.
      
      
      4. 
    
    4. The answer is checked, or retried
      
      
      validate() accepts any number of menu actions but rejects unknown action names, missing fields (a comment with no text,
      a post with no title) or a post in a subreddit that doesn't exist. A rejected answer is retried twice with a new seed. After three
      failures the screen is saved as unreadable (0.08% of round 101) and left out of every table.
      
      
      5. 
    
    5. The baseline: the same AI reads its own AI's posts
      
      
      run_v2.py read takes the post set, shuffles it once into a fixed ring (the same order for every reader AI), and
      gives each user the whole ring starting at their own evenly spaced point, skipping their own post. Each post is one screen.
      
      
      6. 
    
    6. Eight screens at a time
      
      
      A thread pool keeps 8 calls in flight; the server answers them together (8 slots, each with room for 8,192 tokens).
      Each answer is written to the step's .jsonl file the moment it arrives, so a crash loses at most the screens in flight.
      
      
      7. 
    
    7. Steps 2-6 repeat for llama, then gemma
      
      
      So all three baselines exist before any cross reading starts (decision LD-40).
      8. 
    
    8. The six cross cells, in growing stages
      
      
      Each AI reads the other two AIs' sets: first each user's first 16 posts, then 32, then 64, then all. If time runs out, all six cells
      are still evenly covered.
      9. 
    
    9. The noise floor
      
      
      Each AI re-reads 4 posts per user of its own set with a different seed. How often it gives the same answer shows how much
      answers wobble by pure chance.
      10. 
    
    10. A manifest closes every step
      
      
      Git commit, fingerprints of the users, post set and prompts, engine and sampling, time, and the unreadable count go into
      .manifest.json. Then the runner makes a local git commit (a checkpoint) and moves on.
      
      
      11. 
    
    11. Wipe
      
      
      Nothing is carried into the next round: every screen is a fresh call with no memory, follows are never applied, and the next
      round writes brand-new post sets.
      12. 
    
    12. On the laptop: copy, analyse, report
      
      
      rsync copies the result folder from the Spark. analyze_v2.py writes the tables and the bias, and make_report_v2.py
      builds the workbook and graphs.
      13. 
  
    
  
    Where OASIS fits. The menu of 27 actions and the shape of the system prompt come from OASIS. run_v2 can also
  replay every recorded action through OASIS's own functions into a real OASIS Reddit database
  (), but the Spark rounds run with the replay off (the runner's default). The
  results come from the recorded answers, not from an OASIS database.

    Sees
      
      
    • The user's description: age, gender, state, city or countryside, schooling, work, Big Five personality (1-10), and how they feel about each of the five topics (love → hate)
      • 
      
    • On a reading screen: the subreddit, the author's username, the title and the body of ONE post
      • 
      
    • The full menu of 27 actions and the answer format
      • 
      
    • V2 only: which model it is (its own name and maker), in the line before the person's description
      • 
    
    
    
    Never sees
      
      
    • Which AI wrote the post. Only the made-up author's username, which is the same in every AI's set
      • 
      
    • Votes, comments or reactions by anyone else (vote counts are hidden)
      • 
      
    • Anything from its earlier screens: every screen is a separate call with no memory
      • 
      
    • Its own posts (they are skipped) or the author's description
      • 
      
    • Other posts at the same time: one post per screen (pages of several posts made AIs stop commenting, log 14.14)
      • 
      
    • Hidden "thinking": switched off for every AI

    06 · Behind the scenes on the Spark
    
  
    The machine, the engine, and what went wrong
    
  
    
    
    The machine
    
      
    NVIDIA DGX Spark honda.csr.uky.edu (UK Computer Science): an ARM computer with a GB10 GPU and 121 GB of memory
      shared by the CPU and GPU. Login kmgo257 (ssh honda: key login since 9 Oct, one connection kept open and
      reused so an overloaded machine can't lock the login out), on campus or over the GlobalProtect VPN. No admin
      rights, no Docker. Shared with another user (hsa303), whose GPU jobs slowed our runs 2-35×.
    
      
    Everything lives in ~/llm_bias/: oasis/ (a git clone; results in oasis/data/llm_bias/v2/),
      engines/llama.cpp/, models/, logs/, env_llamacpp.sh, watchdog.sh.
    
    
    The engine
    
      
    llama.cpp runs each AI as a small web server on the Spark (qwen port 11601, llama 11602, gemma 11603), with all layers on
      the GPU, flash attention, the model's own chat template, and 8 slots of 8,192 tokens. We switched from Ollama to llama.cpp on
      5 Oct (LD-41) because it was 2.5-3× faster and lets every AI use identical sampling settings. Ollama had quietly applied
      different settings per model.
    
      
    Speed with the GPU to ourselves: qwen 0.41 s, llama 0.51 s, gemma 0.95 s per screen (8 at a time).
    
  
    
  
    Safety nets
    
  
    
    
    Resume. Every screen is saved the moment it's answered. On restart, finished screens are skipped and a
    half-written last line is dropped. A run can be killed at any moment and restarted with the same command.
    
    
    STOP time. The runner never starts a step it can't finish before STOP; at the end it stops the AI server and frees the GPU.
    
    
    Preflight. preflight_v2.py runs 110 checks in a 10-user test round, including a hard kill
    and resume. It must say ALL CLEAR after any code change.
    
    
    Watchdog. A cron job checks every 10 minutes and restarts the runner if it has died. It was added after the run was killed
    overnight on 6-7 Oct.

    09 · Results
    
  
    What the AIs did, in plain percentages
    
  
    In short: telling each AI which AI it is (V2) did not change whose posts it liked more.
  The one big change: in V2, llama and gemma did a little less on everyone's posts.
    
  
    Do the AIs favour their own AI's posts? No. llama and gemma treat all three AIs' posts almost the same
  (in V1, llama did about 222-225 actions per 100 posts whoever wrote them, gemma about 94-96). Only qwen cares who wrote a post, and it likes
  gemma's posts best, not its own: in V1, 130 actions per 100 of gemma's posts, 111 per 100 of its own, 104 per 100 of llama's.
  This is not about topic: when gemma's posts are matched to qwen's own on the same topics and the same stances, the gap stays
  (131 vs 113 in V1, 131 vs 110 in V2). It is only a little about length: gemma's posts are longer (median 225 letters, against 163
  for qwen and 128 for llama), but even gemma's short posts get about 119-126 actions per 100 from qwen. So qwen reacts to how gemma
  writes. Note: gemma wrote only 98 posts in all four rounds (qwen 387, llama 418).

  so you can read it straight: "qwen engaged on 93% of the posts it saw." Grey cells = an AI reading posts from its own AI.
